# 시설 데이터 갱신

구현일: 2026-11-12. `feat/facility-refresh`는 화장실·CCTV의 **지역별 전체 목록 비교 갱신**을 구현한다. 정기 실행 등록은 후속 `chore/facility-refresh-schedule` 작업이다.

## 범위와 증분 처리 결정

[화장실 API](https://www.data.go.kr/data/15155058/openapi.do)와 [CCTV API](https://www.data.go.kr/data/15155042/openapi.do)는 `DAT_UPDT_PNT`의 GTE/LT 필터를 제공한다. 하지만 확인한 문서에서 `DAT_UPDT_SE`의 삭제 값, 삭제된 행의 증분 응답 포함 여부, 갱신 시각의 시간대·지연 보장을 확정하지 못했다.

따라서 이번 구현은 해당 코드를 해석하지 않고 원문으로 보존하며, 전체 목록으로 변경과 누락을 확인한다. **증분 수집 및 원본 갱신시각 워터마크는 구현·활성화하지 않았다.** 아래 체크포인트는 전체 목록 반영 완료 기록이며 원본의 증분 커서가 아니다. 최초 설계의 증분 최적화는 공식 삭제·시간 계약 확인 후 별도 작업으로 남긴다.

## 실행

기존 수집기로 생성한 시설 DB와 `.env`의 `PUBLIC_DATA_SERVICE_KEY`를 사용한다. 없는 DB를 갱신 명령으로 자동 생성하지 않는다. Juso 키는 필요 없으며 화장실 좌표 변환은 실행하지 않는다.

```powershell
# 먼저 전체 목록을 받아 갱신 계획 확인 (DB 변경 없음)
python facility_refresh.py --region-code 3740000 --region-code 3830000 --dry-run

# 같은 두 지역의 화장실·CCTV 반영
python facility_refresh.py --region-code 3740000 --region-code 3830000

# 한 종류만 갱신
python facility_refresh.py --region-code 3740000 --types cctv
```

`--types` 기본값은 `toilet,cctv`이며 `--region-code`는 반복 지정한다. 기본 페이지 크기는 100, 종류·지역별 최대 페이지는 100이다. `--page-size`, `--max-pages`, `--database`, `--env-file`로 변경할 수 있다. 재시도를 포함한 HTTP 호출 수는 페이지 수보다 많을 수 있다. dry-run도 실제 API 호출·쿼터를 사용한다.

종류·지역별로 독립적으로 반영한다. 수원 CCTV가 실패해도 안양 화장실 등 다른 범위를 계속 처리한다. 전체 작업이 하나의 트랜잭션인 것은 아니다. 일부 성공 시 최종 상태는 `partial`, 종료코드는 1이다. 모두 성공/검증 완료일 때만 종료코드 0이다.

## 반영 규칙

1. 요청 전 대상 종류·지역의 기존 행, 수집 상태, 누락 증거, 체크포인트를 읽고 지문을 계산한다.
2. 모든 페이지의 총건수·수신 건수·지역·유일 관리번호와 원본 필드를 검사한다. 총건수 변경·중복·잘린 페이지·호출 실패·예산 초과면 시설을 반영하지 않는다.
3. 짧은 쓰기 트랜잭션을 시작하고 대상 DB 지문을 다시 검사한다. 수집 중 다른 작업이 행·좌표·활성 상태 등을 변경했으면 `REFRESH_BASELINE_CHANGED`로 중단한다. 네트워크 호출 중 SQLite 쓰기 잠금을 잡지 않는다.
4. 새 시설은 추가하고 기존 ID는 유지하며 원본 필드를 갱신한다. 화장실 주소가 같으면 지오코딩을 유지하고 바뀌면 좌표를 초기화한다. CCTV의 목적·좌표 변화도 반영한다.
5. 누락 증거·필요한 비활성화·자동 복구·수집 성공 시각·체크포인트를 시설과 같은 트랜잭션에 저장한다. 어느 단계든 실패하면 모두 롤백한다.

원본 API에 고정된 스냅샷 토큰이 없으므로 같은 총건수 안에서 원본이 바뀌는 모든 경우를 검출한다고 보장하지 않는다. 누락 유예와 급감 방어를 함께 적용하는 이유다.

## 누락과 재등장

- 한 번 목록에서 빠진 시설은 그대로 표시하면서 첫 누락 시각과 횟수만 기록한다.
- 이후 성공한 전체 조회에서도 누락되고 **첫 누락 이후 24시간 이상** 지났을 때 비활성화한다. 최소 두 번의 성공한 전체 조회가 필요하다. 즉시 반복 실행만으로 비활성화하지 않는다.
- 실제 행·원본 좌표는 삭제하지 않는다. 누락이 관측되지 않은 실패/dry-run은 누락 횟수나 체크포인트를 전진시키지 않는다.
- 누락 때문에 자동 비활성화한 시설이 다시 나타나면 동일 ID로 복구한다.
- 기존 수동 비활성화는 자동 복구하지 않는다. 현재 수원·안양의 좌표 검토 대상 5건도 유지한다.
- 자동 비활성화된 항목을 수동 검토 상태로 전환할 때는 `FacilityStore.set_active(id, False)`를 사용한다. 이 메서드는 자동 복구 표시도 해제한다. 직접 SQL로 active만 수정하면 수동 판단의 의도를 기록하지 못하므로 사용하지 않는다.

이는 원본의 법적 폐쇄·시설 철거 여부를 확인한 것이 아니라 **목록에서 지속적으로 사라진 시설을 표시에서 제외하는 정책**이다.

## 급감 보호

기존 시설이 있는데 새 목록이 0건이면 `EMPTY_SNAPSHOT_BLOCKED`, 직전 관측 목록의 ID 중 20%를 초과하여 새로 누락되면 `EXCESSIVE_MISSING_BLOCKED`로 중단한다. 단순 총건수만 비교하지 않으므로 동일 건수의 대규모 ID 교체도 감지한다. 이미 누락된 것으로 기록된 ID는 다음 실행의 새 누락 비율에서 제외한다.

실제 원본 변경임을 점검한 경우에만 `--max-missing-ratio`를 0~1 사이로 조정한다. 전체 소멸을 반영하려면 `--allow-empty --max-missing-ratio 1`을 함께 지정한다. 이 옵션들도 24시간·두 번 관측 정책을 생략하지 않는다. 반복되는 실패를 없애기 위해 무조건 보호 옵션을 완화하지 않는다.

## 상태·로그·재실행

- `facility_refresh_state`: 원본·지역별 성공 세대 번호와 UTC `checkpoint_at`.
- `facility_refresh_presence`: 시설 ID별 첫 누락 시각·관측 횟수·자동 비활성 여부.
- `facility_import_state`: 기존 시설 API에서 사용하는 수집 성공/실패 상태.

추가 테이블은 실제 반영 트랜잭션에서 생성한다. 기존 DB 버전 1과 호환되는 보조 테이블이며 읽기 전용 API와 dry-run은 생성하지 않는다. 과거로 돌아간 체크포인트 시각은 `REFRESH_CLOCK_REVERSED`로 거절한다.

실패 시 시설·누락 증거·성공 체크포인트는 유지하고 마지막 수집 실패 상태만 기록한다. 동시 변경이 감지된 오래된 작업은 더 최신 작업의 상태를 실패로 덮어쓰지 않는다. 다음 실행에서 전체 목록을 다시 받아 재검증한다. 중간 페이지부터 재개하는 기능은 없다.

로그는 `.cache/facilities/refresh-runs/*.json`이며 Git에서 제외된다. 원본 응답·키·주소·요청 URL을 기록하지 않는다. 각 범위 완료 후 로그를 갱신한다. 로그 쓰기 실패 시 DB는 이미 반영됐을 수 있으므로 상태를 확인한다.

주요 수치: `new` 신규, `refreshed` 기존 ID 재수집(실제 값이 달라진 행 수는 아님), `missing` 현재 누락 전체, `new_missing` 새 누락, `deactivated` 이번 비활성, `reactivated` 이번 복구. dry-run의 수치·generation·checkpoint_at은 **반영할 경우의 계획**이지 저장된 상태가 아니다.

정기 갱신에는 새 갱신 명령을 사용한다. 기존 `toilet_import.py`, `cctv_import.py`는 최초 적재/검증용으로 남아 있으며 그 명령만 실행하면 누락 추적·재등장 복구를 수행하지 않는다.

## 검증

```powershell
python -m unittest discover -s tests -p test_facility_refresh.py -v
```

추가·변경·24시간 누락 확인·재등장·수동 제외 유지, 지역 격리, 빈 응답/ID 급감 보호, 페이지 오류, 체크포인트 원자성, 동시 변경, dry-run 무변경, 화장실 좌표 무효화를 검증한다. 실제 데이터의 반영 실행과 자동 스케줄 등록은 이 구현 테스트와 구분한다.

2026-11-12 실제 API dry-run 결과: 수원 화장실 588건·CCTV 4,934건, 안양 화장실 258건·CCTV 1,749건을 모두 검증했다. 4개 범위 모두 신규·누락·비활성·복구 예정 건수는 0건이었다. 검증 전후 실제 DB의 SHA-256은 동일했고, 보조 테이블·체크포인트도 생성하지 않았다. 전체 Python 테스트 201개 중 198개 통과·환경 의존 3개 skip, 지도 JavaScript 테스트 통과.

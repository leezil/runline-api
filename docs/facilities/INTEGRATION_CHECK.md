## 재실행

프로젝트 루트에서 실행한다. 기본 실행은 외부 API를 호출하지 않는다.

```powershell
python check_facility_integration.py
# 실제 공공데이터 API를 임시 DB에서 dry-run으로 확인
python check_facility_integration.py --live-dry-run
```

`--database <경로>`로 읽을 원본 DB를 지정할 수 있다. 실제 API 검증에는 `.env` 또는 환경 변수의 `PUBLIC_DATA_SERVICE_KEY`가 필요하며 호출량을 소모한다. Juso API는 호출하지 않는다. 검증 assertion이 꺼지는 `python -O`는 사용하지 않는다.

## 검증 흐름과 운영 DB 보호

1. 갱신·복원 실행기와 같은 운영 DB 잠금을 획득한다. 사용 중이면 실패하며 기다리거나 강제 종료하지 않는다. 직접 실행하는 수집기·좌표 변환기는 별도로 종료해야 한다.
2. 원본 DB의 파일 SHA-256과 SQLite 논리 덤프 해시를 기록한다. 원본은 읽기 전용 연결로만 접근한다.
3. SQLite 온라인 백업을 임시 폴더에 생성하고 무결성 검사 후 다른 임시 DB 경로로 복원한다. 스키마·시설·좌표·비활성 상태·갱신 메타데이터를 포함한 논리 덤프 해시가 원본과 같은지 확인한다.
4. 복원 DB를 사용하는 로컬 전용·API 전용 HTTP 서버를 임의의 loopback 포트에 시작한다. 기존 운영 포트와 ngrok은 사용하지 않는다. 테스트용 토큰은 메모리에서만 생성하며 파일에 저장하지 않는다. 자동 갱신 스케줄러도 시작하지 않는다.
5. 두 포트에서 health 200, 인증 누락 401, 시설 상태 및 지도 조회 200, 잘못된 상태 조회 쿼리 400을 확인한다. 응답은 같은 복원 DB의 직접 조회 결과와 비교한다.
6. 옵션을 켰다면 수원·안양 화장실·CCTV를 실제 API에서 조회하되, 갱신 대상은 반드시 복원된 임시 DB이고 `--dry-run`을 전달한다.
7. 임시 DB 파일·논리 데이터가 그대로인지 확인하고 HTTP 조회를 다시 비교한다. 원본 파일·논리 데이터도 실행 전과 같은지 최종 확인한다.
8. 테스트 서버와 임시 DB를 정리한다. `.cache/facilities/integration-last.json`에 결과를 저장한다. 실제 API dry-run의 상세 로그는 기존 `refresh-runs` 폴더에 남는다. DB 밖의 잠금·로그 파일은 생성될 수 있다.

종료 코드 0 및 `status: passed`가 성공이다. `production_unchanged`, `copy_unchanged`, `backup_restore_equal`이 모두 true여야 한다. 실패 시 고정 오류 코드만 출력하며 키·원본 예외·임시 파일 경로는 출력하지 않는다. JSON 보고서는 Git에서 제외된다.

## 검증 범위의 한계

이 검증은 데이터 복원과 실제 HTTP 핸들러의 연동을 확인한다. 외부 ngrok 연결, 다른 기기에서의 접속, 자정 실시간 예약 실행, 좌표 API 승인 및 실제 좌표 변환은 포함하지 않는다. 실제 갱신 반영이나 누락 비활성화를 운영 DB에 수행하지 않는다. 재시도·트랜잭션·중단 복구·복사 실패 롤백은 별도 회귀 테스트로 확인한다.

좌표 승인 후에는 별도 백업 → 5건 시범 변환 → 위치 검토 → 전체 변환 → 상태 조회를 진행한다. 운영 DB에 실제 갱신을 반영하는 검증은 별도 작업으로 진행한다.
